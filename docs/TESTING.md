# 테스트 기준

HomeFin Mate의 모든 모듈에 공통으로 적용하는 테스트 기준입니다.
기능별 명세는 [test-cases/](test-cases/README.md), 결함 목록은 [known-issues.md](known-issues.md), 실행 결과는 [TEST_REPORT.md](TEST_REPORT.md)에 있습니다.

---

## 1. 목적과 원칙

금융 계산과 개인정보를 다루므로 **틀린 숫자, 다른 사람 데이터 노출, 내부 정보 노출**을 테스트로 먼저 막습니다.

- **요구사항과 현재 구현을 구분합니다.** 구현되지 않은 동작(예: 연이율 0%의 월 상환액, #34)을 기대 결과로 쓰지 않습니다. 기준이 정해지지 않은 것은 명세에 `확인 필요`로 남깁니다.
- **실행한 결과만 결과로 셉니다.** 작성만 한 테스트, 결과 XML이 없는 테스트는 `미실행`입니다.
- **통과율을 위해 테스트를 지우거나 단언을 약하게 바꾸지 않습니다.**
- **테스트를 통과시키려고 제품 코드를 고치지 않습니다.** 결함이 드러나면 [현재 동작 고정](#현재-동작-고정-테스트) 테스트와 알려진 문제로 남기고, 수정은 별도 PR에서 합니다.
- **기대값은 코드에서 복사하지 않습니다.** 계산 결과는 공식으로 따로 계산하거나 외부 계산기로 확인한 값을 씁니다 (예: TC-LOAN-202).
- **처음부터 통과한 중요한 테스트는 실제로 결함을 잡는지 확인합니다.** 제품 코드를 일부러 틀리게 바꿔(변이) 그 테스트가 실패하는지 봅니다. 확인 기록은 [TEST_REPORT.md](TEST_REPORT.md)에 남깁니다.

## 2. 테스트 종류

| 종류       | 도구                                             | 범위                                       | 예                                               |
| ---------- | ------------------------------------------------ | ------------------------------------------ | ------------------------------------------------ |
| 단위       | JUnit 5 + Mockito                                | 클래스 하나. 의존성은 Mock                 | `LoanServiceTest`, `JwtUtilTest`                 |
| 저장소     | `@DataJpaTest` + H2                              | Repository, DB 제약                        | `UserRepositoryTest`, `RiskWatchClientAuditTest` |
| 외부 연동  | MockRestServiceServer                            | HTTP 클라이언트의 재시도·타임아웃·fallback | `RiskWatchClientTest`                            |
| HTTP 통합  | `@SpringBootTest` + `@AutoConfigureMockMvc` + H2 | 보안 필터 → 컨트롤러 → 서비스 → DB 전체    | `SecurityAccessTest`, `AnalyzeIntegrationTest`   |
| Python API | pytest + FastAPI TestClient                      | 지역 분석 API                              | `tests/test_analysis.py`                         |
| 프론트     | Vitest + jsdom                                   | 토큰 저장, axios 인터셉터                  | `src/**/*.test.js`                               |

- 인증·인가, 입력 검증, 오류 응답처럼 **필터나 컨트롤러를 거쳐야 의미가 있는 동작**은 HTTP 통합 테스트로 확인합니다. 서비스 단위 테스트만으로는 주소 규칙이 바뀌어도 알 수 없습니다.
- 성능은 테스트가 아니라 별도 측정으로 다룹니다 ([performance.md](performance.md), k6).

## 3. 테스트 설계 관점

새 기능이나 수정마다 아래 네 관점을 검토하고, 해당 없는 관점은 명세에 이유를 적습니다.

| 분류 | 확인할 것                                                                                                                                                     |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 정상 | 대표 입력의 결과값, 저장되는 값, 감사·이용 기록                                                                                                               |
| 예외 | 필수값 누락, 형식 오류, 외부 서비스 실패(연결 실패·타임아웃·5xx·잘못된 응답), 중간 단계 실패 시 저장 상태                                                     |
| 경계 | 0, 1, 최대값(기간 600개월, 연이율 99.9999, DTI 상한 999.9999), 음수, 판정 기준값(DTI 0.60), 빈 목록                                                           |
| 보안 | 토큰 없음·만료·변조·다른 키, 일반 사용자의 관리자 API, 다른 사용자 데이터 접근, 응답·로그의 내부 정보(SQL, 클래스 이름)와 개인정보(이메일, 소득), 암호문 변조 |

금융 계산은 다음을 함께 확인합니다.

- 공식과의 일치
- 반올림 자릿수 (월 상환액 소수 2자리, DTI 소수 4자리)
- 값 사이 관계 (총상환액 = 월 상환액 × 개월, 총이자 = 총상환액 − 원금)
- 저장 컬럼의 범위

## 4. 테스트 데이터와 환경변수

- **비밀값:** 테스트는 `backend/src/test/resources/application-test.yml`의 **테스트 전용 키**만 씁니다. 실제 `.env` 값이 필요한 테스트는 만들지 않습니다(CI에는 `.env`가 없습니다).
- **데이터:** 이메일은 `ApiTestSupport.uniqueEmail()`로 매번 새로 만듭니다. 같은 H2 DB를 여러 테스트가 공유하기 때문에 데이터가 섞이지 않게 하기 위해서입니다.
- **금액·소득:** 실제 개인의 값이 아닌 예시 값만 씁니다.
- **로그 출력:** 테스트 로그에 비밀번호·토큰·키를 출력하지 않습니다.

## 5. 외부 API와 DB

| 의존성           | 테스트에서의 처리                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| MySQL            | H2 메모리 DB (`application-test.yml`). MySQL에서만 다른 동작(오류 메시지 문구 등)은 명세에 적습니다     |
| RiskWatch        | 단위: MockRestServiceServer. 통합: 닫힌 포트 `127.0.0.1:9`로 보내 항상 연결 실패 → fallback             |
| Python 지역 분석 | Python 쪽은 TestClient로 직접 테스트. 백엔드 통합 테스트에서는 닫힌 포트 → 분석 불가(`available=false`) |
| 시간·난수        | 결과가 시간·난수에 따라 바뀌는 값은 직접 비교하지 않고 형식·관계만 확인 (예: IV는 "매번 다름"만 확인)   |

외부 주소를 닫힌 포트로 고정하는 이유는, PC에 Docker 서비스(8200, 8120)가 떠 있으면 결과가 달라지기 때문입니다. 테스트는 언제 어디서 돌려도 결과가 같아야 합니다.

## 6. 실행 명령과 순서

저장소 루트 기준입니다.

```bash
cd backend && mvn test                                               # 1. 백엔드 (+ JaCoCo: target/site/jacoco/index.html)
cd python-service && python -m pytest -q --junitxml=test-results/pytest.xml   # 2. Python (가상환경 활성화 후)
cd frontend && npm test                                              # 3. 프론트 (결과: test-results/junit.xml)
python scripts/tc_status.py                                          # 4. 명세 ↔ 테스트 ↔ 결과 대조
```

- 특정 클래스만 돌릴 때: `mvn test -Dtest=SecurityAccessTest`
- **제품 코드를 바꿔 가며 확인했다면 `target`을 지우고 다시 빌드합니다**(`rm -rf target && mvn test`). 이전 빌드 결과물이 남아 엉뚱한 결과가 나온 적이 있습니다.
- CI(GitHub Actions)는 PR과 main push마다 1~4를 실행합니다. 4에서 불일치·실패·미실행이 있으면 실패합니다.

## 7. 실패 분석과 재검증

테스트가 실패하면 원인을 아래 넷 중 하나로 분류하고 기록한 뒤 고칩니다.

| 원인             | 판단 근거                                                | 조치                                                                |
| ---------------- | -------------------------------------------------------- | ------------------------------------------------------------------- |
| 제품 결함        | 요구사항 또는 명확한 상식(0으로 나누기 등)과 다르게 동작 | 알려진 문제에 등록. 이번 범위가 아니면 현재 동작 고정 테스트로 남김 |
| 테스트 코드 문제 | 잘못된 기대값, 빠진 `@Test`, 공유 데이터 의존            | 테스트 수정 (단언을 약하게 바꾸는 수정은 금지)                      |
| 환경 문제        | 이전 빌드 결과물, 포트 사용 중, `.env` 유무              | 환경 정리 후 재실행. 반복되면 테스트를 환경과 분리                  |
| 요구사항 불명확  | 기준이 정해지지 않음 (예: 보금자리론 다자녀 인원 정의)   | 명세에 `확인 필요`, 기대 결과를 임의로 정하지 않음                  |

고친 뒤에는 **실패했던 테스트 → 같은 클래스 → 전체** 순서로 다시 실행합니다.

## 8. 결과 보고 형식

작업 보고나 PR 본문에는 다음을 적습니다.

1. 수정·추가한 파일
2. 실행한 명령
3. 결과: 실행 수, 통과·실패·건너뜀. 실행하지 못한 것은 이유와 함께 **미실행**
4. 발견한 결함 (알려진 문제 번호)
5. 검증하지 못한 영역

전체 결과는 [TEST_REPORT.md](TEST_REPORT.md)에 같은 형식으로 남깁니다.

**커버리지 사용 원칙**

- 커버리지는 "실행되지 않은 코드가 어디인지" 찾는 용도로만 씁니다.
- 커버리지가 높다고 결과가 맞다는 뜻은 아닙니다. 그래서 기준치로 빌드를 실패시키지 않습니다.

## 9. 우선순위와 위험도

| 등급 | 기준                                                          | 예                                            |
| ---- | ------------------------------------------------------------- | --------------------------------------------- |
| P0   | 데이터 손상, 권한 우회, 민감정보 대량 노출                    | 다른 사용자 계산 이력 조회 가능               |
| P1   | 금융 계산 오류, 핵심 API 장애, 인증·인가 오류, 내부 정보 노출 | 연이율 10% 저장 실패(#1), 응답에 SQL 노출(#4) |
| P2   | 일반 기능 오류, 예외 처리 부족, 회귀 테스트 부족              | 로그에 이메일 평문(#83)                       |
| P3   | 낮은 위험의 보완, 테스트 편의                                 | traceId 헤더                                  |

같은 등급이면 사용자 수가 많은 경로(로그인, 대출 계산)를 먼저 합니다.

## 10. AI가 제안한 테스트를 쓰는 방법

AI(Claude Code)는 **테스트 설계·검토·실패 분석을 돕는 도구**로만 씁니다.

- 테스트 실행 자체에는 AI가 들어가지 않습니다. CI와 스크립트는 같은 입력이면 항상 같은 결과를 냅니다.
- AI API를 호출하는 자동화는 두지 않습니다.

| 단계    | 하는 일                                                                                | 기록 위치                                  |
| ------- | -------------------------------------------------------------------------------------- | ------------------------------------------ |
| 1. 제안 | AI가 코드와 기존 테스트를 읽고 정상·예외·경계·보안 관점의 빈 곳을 제안                 | 작업 대화 / PR 본문 "AI 제안"              |
| 2. 검토 | 사람이 실제 코드·요구사항과 대조. 구현되지 않은 동작, 기준이 없는 동작은 채택하지 않음 | 명세의 `확인 필요`, `자동화 안 함: 사유`   |
| 3. 명세 | 채택한 항목에 ID를 붙여 [test-cases/](test-cases/README.md)에 추가                     | 명세 표                                    |
| 4. 작성 | 테스트 작성. `@DisplayName("[TC-…]")` 등으로 ID 연결                                   | 테스트 코드                                |
| 5. 실행 | 실제 실행. 결과 XML 생성                                                               | `target/surefire-reports`, `test-results/` |
| 6. 분석 | 실패 원인을 7번 기준으로 분류                                                          | PR 본문, 알려진 문제                       |
| 7. 확인 | 중요한 테스트는 변이로 실제로 실패하는지 확인                                          | TEST_REPORT                                |
| 8. 기록 | 결과, 미검증 영역, 채택하지 않은 제안과 이유                                           | TEST_REPORT                                |

**채택 기준**

- **채택합니다:**
  - 코드에서 실제로 그 경로가 실행될 수 있음
  - 기대 결과가 요구사항이나 명확한 사실(공식, 규격, 보안 원칙)로 정해짐
  - 실행할 때마다 결과가 같음
- **채택하지 않습니다:**
  - 존재하지 않는 기능이나 파일을 가정한 제안
  - 기대 결과를 AI가 정한 제안
  - 결과가 매번 달라지는 동시성·시간 의존 테스트 (설계를 바꿔서 결정적으로 만들 수 있을 때만)
  - 실행 시간이 너무 긴 테스트 (예: 1억 개월 계산 → 측정으로 대체)

## 현재 동작 고정 테스트

결함인 동작을 "지금은 이렇게 동작한다"고 단언하는 테스트입니다. 이름과 명세에 ⚠️와 문제 번호를 붙입니다.

- 확인하기 어렵거나 고친 뒤 결과가 바뀌는 것을 보여 줘야 하는 결함에만 만듭니다.
  - 예: DB 제약, 서비스 간 연동, 트랜잭션, 정보 노출
- 사소하고 고치는 방법이 명확한 결함은 테스트 없이 명세의 3xx 행과 알려진 문제에만 적습니다.
- 결함을 고치는 PR에서 기대 결과를 올바른 동작으로 뒤집고 ⚠️를 뗍니다. **지우지 않습니다.**
