# 성능 측정 계획과 결과

HomeFin Mate를 다시 구현하며 찾은 성능 문제를 **측정 → 개선 → 같은 조건으로 다시 측정**하는 순서로 고치고, 그 결과를 수치로 남깁니다.

## 원칙

- **실제로 잰 값만** 기록합니다. 예상치는 "예상"이라고 따로 표시합니다.
- 개선 전후는 **같은 PC, 같은 데이터, 같은 시나리오**로 잽니다. 조건을 표에 함께 적습니다.
- 워밍업 30초 뒤 측정하고, **3번 반복한 중앙값**을 씁니다.
- 개선 전 코드는 `perf-baseline` 태그로 고정해, 언제든 다시 잴 수 있게 합니다.
- 실제 사용 상황(외부 시스템 장애, 데이터 누적)에서 생기는 문제만 다룹니다. 체감되지 않는 미세 최적화는 하지 않습니다.

## S1. 외부 시스템 장애 시 응답 시간

| 항목      | 내용                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------ |
| 관련 문제 | #35 타임아웃 설정 미사용, #36 4xx 재시도·backoff 없음, #42 일부 예외에서 fallback 실패           |
| 상황      | RiskWatch가 응답하지 않음 (가짜 RiskWatch가 응답 지연)                                           |
| 요청      | `POST /api/analyze`                                                                              |
| 지표      | 응답 시간 p50 / p95 / p99, 처리량(RPS), 오류율                                                   |
| 개선      | 타임아웃을 설정에서 읽고 짧게 조정, 5xx·타임아웃만 재시도 + backoff, 서킷 브레이커(Resilience4j) |

**사전 측정 (2026-10-14, 개선 전 참고값)**
분석 1건이 **30.4초** 걸림. 가짜 RiskWatch가 15초를 쓰는데 응답 타임아웃이 10초라 3번 모두 시간 초과 → fallback.

| 조건                    | p50     | p95     | p99     | RPS   | 오류율 |
| ----------------------- | ------- | ------- | ------- | ----- | ------ |
| 개선 전                 | 30.11초 | 30.18초 | 30.18초 | 0.166 | 0%     |
| 타임아웃·재시도 조정 후 |         |         |         |       |        |
| 서킷 브레이커 적용 후   |         |         |         |       |        |

**측정 조건 (개선 전, 2026-10-15, `perf-baseline` 코드)**

- 가짜 RiskWatch 지연 60초 (응답하지 않는 장애), 동시 사용자 5명 × 3분, 워밍업 30초 후 3번 반복한 중앙값
- 3번의 결과: p50 30.11 / 30.10 / 30.12초, p95 30.25 / 30.15 / 30.18초, 매번 분석 30건, 오류 0건
- 오류율이 0%인 이유: 3번 시도가 모두 실패하면 fallback(`available=false`)으로 200을 돌려주기 때문. **응답은 성공이지만 사용자는 매번 30초를 기다림**
- 동시 사용자 5명이 각자 30초씩 기다려서 처리량은 초당 0.166건 (= 5 ÷ 30초)
