**읽을 때 주의할 점**

- 개선 전 숫자 중 일부는 "느린 상태"가 아니라 **장애 상태**입니다. S2a의 10초는 커넥션 대기 타임아웃 값이고, 개선 후 0.1초 안팎은 장애가 없을 때의 평소 응답 시간과 같은 수준입니다. 그래서 "몇 배 빨라졌다"보다 **"장애가 번지지 않게 했다", "동작하지 않던 기능을 동작하게 했다"**로 읽어야 합니다.
- S1의 30초 → 2초는 타임아웃 값을, 2초 → 0.04초는 호출 자체를 건너뛴 결과(서킷 브레이커)입니다. 속도보다 **장애 중 기다리지 않는 것**과 **장애 난 시스템에 보내는 호출 수(445 → 30건)**가 의미 있는 지표입니다.

- 남은 것: 프론트 번들·Python 이미지 크기(부가 항목). 계산 이력 페이징(#51)은 기능으로 추가했고 다시 측정하지는 않았습니다

## 원칙

- **실제로 잰 값만** 기록합니다. 예상치는 "예상"이라고 따로 표시합니다.

**측정 조건 (개선 전, 2026-10-15, `perf-baseline` 코드)**

- 가짜 RiskWatch 지연 60초 (응답하지 않는 장애), 동시 사용자 5명 × 3분, 워밍업 30초 후 3번 반복한 중앙값
- 3번의 결과: p50 30.11 / 30.10 / 30.12초, p95 30.25 / 30.15 / 30.18초, 매번 분석 30건, 오류 0건

- 동시 사용자 5명이 각자 30초씩 기다려서 처리량은 초당 0.166건 (= 5 ÷ 30초)

**측정 조건 (타임아웃·재시도 조정 후, 2026-10-15, 같은 조건)**

- 개선: RiskWatch 전용 타임아웃을 설정에서 읽음(연결 1초·응답 2초), 응답 타임아웃·4xx·SUCCESS가 아닌 응답은 재시도하지 않고 5xx·연결 실패만 backoff 후 재시도, 어떤 예외든 fallback
- 3번의 결과: p50 2.05 / 2.05 / 2.04초, p95 2.10 / 2.08 / 2.06초, 분석 440 / 440 / 445건, 오류 0건
- **p95 30.18초 → 2.08초 (93% 감소), 처리량 초당 0.166건 → 2.429건 (약 14.6배)**

**측정 조건 (서킷 브레이커 적용 후, 2026-10-15, 같은 조건)**

- 개선: Resilience4j 서킷 브레이커. 최근 10번 시도 중(최소 5번) 50% 이상 실패하면 10초 동안 RiskWatch를 부르지 않고 바로 fallback, 10초 뒤 2번만 시험 호출.
  5xx·연결 실패·타임아웃만 실패로 셈 (4xx·SUCCESS 아닌 200은 세지 않음)
- 같은 코드 기준 비교를 위해 적용 직전(13-2c 코드)을 다시 측정함. 가짜 RiskWatch가 받은 요청 수를 함께 셈 (`GET /stats`)

- 3번의 결과 (적용 후): p95 0.06 / 0.04 / 0.03초, RiskWatch 호출 33 / 30 / 30건, 새 감사 기록 62 / 60 / 60건.
  적용 직전: p95 2.10 / 2.04 / 2.04초, 호출 445 / 445 / 445건
- RiskWatch 호출 30건은 설정과 맞음: 10초 차단 → 시험 호출 2건(각 2초 타임아웃 후 실패) → 다시 차단, 3분에 약 15번 반복 × 2건.
  max 2.1초는 이 시험 호출을 맡은 요청
- **처리량(RPS)은 비교하지 않음.** 동시 사용자 5명이 쉬지 않고 요청을 보내는 시나리오라, 응답이 0.02초가 되면 요청 수가 초당 약 200건으로 늘어날 뿐 실제 처리 능력을 뜻하지 않음
- **적용 중 발견한 문제와 수정:** 처음에는 차단 중에도 요청마다 "연동 실패" 감사 기록을 남겨 **측정 9분 동안 87,895건**이 쌓였음
  (응답이 빨라진 만큼 실패 기록도 빨리 쌓임). 실제로 호출했다가 실패한 경우만 기록하고, 차단으로 건너뛴 요청 대신 **상태가 바뀔 때 한 번**
  (`RISKWATCH_CIRCUIT_CLOSED_TO_OPEN` 등) 기록하도록 바꿈 → 3분에 60건 (시험 호출 실패 30건 + 상태 변경 30건)

**RiskWatch 타임아웃을 2초로 정한 근거**

1. **목표 응답 시간**: 통합 분석은 사용자가 화면에서 결과를 기다리는 요청이라, 장애 상황에서도 **p95 3초 이내**를 목표로 정했습니다 (설계 목표).
2. **내부 처리 시간 실측** (2026-10-15, 가짜 RiskWatch 지연 0초, 지역 입력 없음, 1분 × 3회):
   대출 계산·정책 추천·저장 등 RiskWatch를 뺀 나머지 처리는 **p95 0.05초** (0.04 / 0.05 / 0.05초), 동시 5명일 때 p95 0.09초.
   → 목표 3초 중 거의 전부를 외부 호출에 쓸 수 있음
3. **위험 평가는 부가 기능**: 실패해도 fallback으로 대출·정책 결과는 그대로 보여 줍니다. 오래 기다려서 평가를 받는 것보다, 빨리 포기하고 "평가 불가"를 보여 주는 편이 사용자에게 낫다고 판단했습니다.
4. **값**: 연결 1초 + 응답 2초. 응답 타임아웃은 재시도하지 않으므로 RiskWatch가 멈춰도 한 번의 분석은 약 2초(연결이 늦은 경우 최대 약 3초)에 끝납니다. 5xx·연결 실패 재시도는 즉시 실패하는 경우라 backoff(0.2초 + 0.4초)만 더해집니다.

**한계와 운영 시 조정 방법**

- 학습 저장소에는 실제 RiskWatch 서버가 없어서 **RiskWatch의 정상 응답 시간은 측정하지 못했습니다.** 2초는 목표 응답 시간에서 역산한 값입니다.
- 운영에서는 RiskWatch 응답 시간 p99를 모니터링하고, 타임아웃을 p99의 1.5~2배 정도로 맞춥니다. 그 값이 2초를 넘으면 목표 응답 시간과 위험 평가 성공률 사이에서 다시 정합니다.
- 코드 수정 없이 환경변수(`RISKWATCH_CONNECT_TIMEOUT_MS`, `RISKWATCH_TIMEOUT_MS`)로 바꿀 수 있습니다.

**측정 조건**: 동시 요청 없이 1명이 차례로 요청. 리포트·계산 이력은 30번 × 3회, 관리자 조회는 매번 백엔드를 재시작한 뒤 1번 × 3회(타임아웃 300초). 백엔드 메모리 1GB(JVM 힙 최대 248MB).

| 요청               | 조건    | p50      | p95      | 결과                                 | DB가 읽은 행 (`EXPLAIN`)                                                     |

- 3번의 결과: 리포트 p50 57 / 53 / 55ms, 계산 이력 p50 52 / 59 / 50ms
- 관리자 조회: 1번은 27.9초 만에 연결이 끊김(EOF), 나머지 5번은 300초 동안 응답 없음. 매번 백엔드 로그에 `java.lang.OutOfMemoryError: Java heap space`
- 한 번의 조회 동안 힙 사용량이 최대치(248MB 중 245MB)까지 참 (actuator `jvm.memory.used`)
- `EXPLAIN` 원문: 계산 기록 `type: ALL, key: NULL, rows: 99722, Extra: Using where; Using filesort` / 감사 기록 `type: ALL, key: NULL, rows: 994307, Extra: Using filesort` (`rows`는 MySQL 통계로 계산한 **추정치**이고, 실제 행 수는 1,000,472건)
- 해석: 리포트·이력은 지금 데이터 양에서는 수십 ms지만 사용자 수에 비례해 느려지는 구조이고, 관리자 조회는 **로그 100만 건에서 기능 자체가 동작하지 않음**

**개선 후 (2026-10-16, 같은 데이터·같은 조건)**

- 개선: `loan_simulations(user_id, created_at)`·로그 표 3개 `created_at` 인덱스, 관리자 조회는 DB에서 최신 100건만(`findTop100…`) + 연동 실패 필터를 DB 쿼리(`LIKE '접두사%'`)로, 리포트는 `COUNT` + 최근 5건(`LIMIT 5`) (#45, #51)
- 데이터: 감사 기록은 개선 전 측정(1,000,472건)보다 1.3% 많은 1,013,702건 (그 사이 S1·S2 측정에서 쌓인 연동 실패 기록). 계산 기록은 같음
- 3번의 결과: 리포트 p50 21 / 18 / 17ms·p95 47 / 32 / 34ms, 계산 이력 p50 14 / 13 / 12ms·p95 33 / 32 / 21ms, 감사 기록 133 / 134 / 187ms, 연동 실패 130 / 239 / 173ms
- 관리자 조회는 매번 백엔드를 재시작한 뒤 첫 요청 1번이라 JVM 준비 시간이 포함됨. 6번 모두 `OutOfMemoryError` 없음
- `EXPLAIN ANALYZE` (실제로 읽은 행): 감사 기록 100행, 계산 기록 100행. 연동 실패는 최신 쪽에 연동 실패 기록이 몰려 있어 192행만 읽었지만,
  시드 데이터 비율(연동 실패 약 1%)이라면 100건을 찾을 때까지 약 1만 행을 읽게 됨 (추정, 측정 안 함). 그래도 100만 행을 앱으로 가져오던 것과는 다름
- 해석: **관리자 조회는 "동작 안 함(메모리 부족) → 0.2초 안팎"**. 리포트·이력은 응답 시간이 약 3분의 1로 줄었지만(p50 55 → 18ms, 52 → 13ms) 원래도 빨랐음.
  더 중요한 변화는 **읽는 행 수가 사용자 수와 무관해진 것** (10만 행 전체 스캔 + 정렬 → 내 기록 100행)
- 이후: 계산 이력은 `?page=&size=` 페이지 조회로 바꿈(기본 20건, 최대 100건, 대시보드는 최근 100건, #51). 응답 크기가 기록 수와 무관해졌지만 S3를 다시 측정하지는 않음
